# レビュー方針書

## 1. レビュー観点・チェック項目

### 1.1 Correctness (正しさ)
- [ ] 要件・仕様 (`docs/product.md`, `docs/api.md`) を満たしているか
- [ ] エッジケース・境界値・エラーケースが考慮されているか
- [ ] 型安全性: `any` 未使用、推論正常、コンパイルエラー 0 件
- [ ] テスト: 正常系・異常系カバー、TDD サイクル遵守
- [ ] 並行処理・競合状態 (楽観的 UI 含む) の考慮

### 1.2 Maintainability (保守性)
- [ ] 単一責任原則: 関数・コンポーネント・モジュールが適切に分割されているか
- [ ] 命名: 意図が明確、略語避け、[`docs/glossary.md`](glossary.md#命名規則) 準拠
- [ ] 重複排除: DRY 原則、共通ロジックはユーティリティ・フック・共有パッケージへ
- [ ] 依存方向: 循環依存なし、レイヤーアーキテクチャ遵守
- [ ] コメント: 「なぜ」を説明、「何を」はコードで自明に

### 1.3 Performance (性能)
- [ ] 不要な再レンダリング防止: `React.memo`, `useMemo`, `useCallback` 適切使用
- [ ] バンドルサイズ: 非同期インポート、Tree-shaking 阻害なし
- [ ] DB クエリ: N+1 問題なし、インデックス適切、取得カラム最小限
- [ ] ネットワーク: 過剰フェッチ・ウォーターフォールなし

### 1.4 Security (セキュリティ)
- [ ] 入力バリデーション: Zod スキーマ適用済み (フロント・バック両方)
- [ ] SQL インジェクション: Drizzle パラメータ化クエリのみ使用
- [ ] XSS: `dangerouslySetInnerHTML` 未使用、React 自動エスケープ信頼
- [ ] 認証・認可: スコープ外だが、将来拡張ポイント確保されているか
- [ ] 秘密情報: ハードコーディング・コミット・ログ出力なし

### 1.5 Accessibility (アクセシビリティ)
- [ ] セマンティック HTML: 適切な要素使用 (`<button>`, `<form>`, `<label>` 等)
- [ ] キーボード操作: フォーカス移動・操作可能、タブ順序自然
- [ ] フォーカス表示: アウトライン非消去、カスタムフォーカススタイルあり
- [ ] ARIA: 必要最小限 (`aria-label`, `aria-live` 等) 適切使用
- [ ] カラーコントラスト: WCAG AA 以上 (テキスト 4.5:1)

### 1.6 Developer Experience (開発体験)
- [ ] 型推論: Hono RPC / Conform / Drizzle-Zod の恩恵受けられるか
- [ ] エラーメッセージ: 開発者が原因特定しやすいか
- [ ] ホットリロード: 変更反映が高速か
- [ ] デバッグ: ソースマップ正常、ブレークポイント有効

## 2. PR レビュープロセス

### 2.1 レビュー依頼のタイミング
| フェーズ | アクション | 責任者 |
|----------|------------|--------|
| **実装前** | 設計・アプローチ相談 (Issue / Draft PR) | 作成者 → レビュアー指名 |
| **実装中** | WIP PR で進捗共有、早期フィードバック | 作成者 |
| **実装完了** | Ready for Review 変更、セルフレビュー実施済み | 作成者 → レビュアーアサイン |
| **レビュー中** | 指摘対応・再レビュー依頼 | 作成者 ↔ レビュアー |
| **承認後** | マージ (Squash & Merge 推奨) | 作成者 |

### 2.2 レビュアー指名ルール
| 変更領域 | 必須レビュアー | 推奨レビュアー |
|------------|----------------|----------------|
| **Backend API** (`apps/backend/src/index.ts`) | バックエンド担当 | フロントエンド担当 (型影響確認) |
| **Frontend UI** (`apps/frontend/app/routes/board.tsx`) | フロントエンド担当 | デザイン・アクセシビリティ担当 |
| **Shared Schema** (`packages/shared/`, `apps/backend/src/db/schema.ts`) | 両担当者 | - |
| **Architecture/Config** (`docs/`, `pnpm-workspace.yaml`, `package.json`) | 全員 | - |
| **Security/Auth** | セキュリティ担当 (将来) | 全員 |

### 2.3 レビュー期間目安
- **初回レビュー**: PR 作成から 24 時間以内
- **再レビュー**: 対応コミットから 12 時間以内
- **緊急修正 (hotfix)**: 即時〜数時間

## 3. 承認ルール

### 3.1 マージ条件 (Branch Protection Rules)
- [ ] **必須承認数**: 1 以上 (将来 2 以上に強化予定)
- [ ] **CI パス必須**: `typecheck`, `lint`, `test` すべてグリーン
- [ ] **会話解決必須**: すべてのレビューコメントが解決済み
- [ ] **最新 main へリベース/マージ済み**: コンフリクトなし
- [ ] **Draft 解除済み**: "Ready for Review" 状態

### 3.2 例外的マージ許可
| 条件 | 承認者 | 事後対応 |
|------|--------|----------|
| **緊急ホットフィックス** (本番障害) | テックリード 1 名 | 24 時間以内に事後レビュー実施 |
| **ドキュメントのみ** (`docs/`, `README.md`) | 作成者セルフマージ可 | - |
| **依存更新** (`pnpm update`, `renovate` PR) | CI パスのみで可 | 破壊的変更時はレビュー必須 |

## 4. レビューコメントの粒度・トーン ガイドライン

### 4.1 コメント分類 (GitHub レビューコメント機能活用)

| 分類 | ラベル | 用途 | 例 |
|------|--------|------|-----|
| **必須修正** | `🔴 Must Fix` | バグ・仕様違反・セキュリティ・CI 失敗 | "この条件分岐で `null` が返るケースが漏れています" |
| **推奨修正** | `🟡 Should Fix` | 保守性・パフォーマンス・命名・テスト不足 | "この関数名は `fetchBoard` ではなく `loadBoardData` の方が意図が明確です" |
| **提案・質問** | `🔵 Suggestion` | 代替案・設計相談・学習目的 | "ここで `useCallback` 使うと再レンダリング減らせますが、依存配列どうします？" |
| **称賛・確認** | `🟢 Good` | 好事例・学び・承認 | "楽観的 UI の実装、きれいに分離されてて良いですね！" |

### 4.2 トーン原則
- **建設的**: 批判でなく改善提案、「なぜダメか」「どうすれば良いか」をセットで
- **具体的**: ファイル名・行番号・コード片を示す
- **敬意**: 作成者の意図・努力を認める、人格否定しない
- **簡潔**: 1 コメント 1 論点、長文は要約+詳細リンク

### 4.3 良いコメント例
```markdown
🔴 Must Fix: apps/backend/src/index.ts:142
`deleteMany` の戻り値 `count` で存在確認していますが、同時に複数リクエスト来た場合 race condition で誤判定の可能性があります。
`findUnique` で存在確認してから `delete` するか、トランザクションで囲むことを推奨します。
参考: https://github.com/org/repo/pull/123#discussion_r456
```

### 4.4 避けるべきコメント
- ❌ "ここ変だよ" (具体性欠如)
- ❌ "普通こう書くよね" (主観・暗黙知押し付け)
- ❌ "前も言ったけど" (感情的・建設的でない)
- ❌ スタイルのみの指摘 (Prettier/ESLint で自動化すべき)

## 5. セルフレビュー チェックリスト

PR 作成前に作成者自身で確認する項目：

### 5.1 コード品質
- [ ] `pnpm typecheck` パス
- [ ] `pnpm lint` パス
- [ ] `pnpm test` パス
- [ ] コンソールログ・デバッグコード削除済み
- [ ] `console.log` / `debugger` 残っていない

### 5.2 設計・ドキュメント同期
- [ ] 影響する設計ドキュメント (`docs/`) 更新済み (同一コミット)
- [ ] `docs/api.md` 更新済み (API 変更時)
- [ ] `docs/glossary.md` 更新済み (新用語・命名導入時)
- [ ] `README.md` 更新済み (概要・リンク変更時)

### 5.3 テスト
- [ ] 新機能に対応するテスト追加済み (正常系・異常系)
- [ ] 既存テストが壊れていない
- [ ] テスト名が「〜する」「〜ではない」形式で意図明確

### 5.4 セキュリティ・パフォーマンス
- [ ] 入力バリデーション (Zod) 適用済み
- [ ] 生 SQL / 文字列結合クエリなし
- [ ] `dangerouslySetInnerHTML` 未使用
- [ ] 秘密情報・個人情報含まない

### 5.5 Git・コミット
- [ ] コミットメッセージが Conventional Commits 形式
- [ ] 論理的単位でコミット分割 (1 PR = 複数コミット可)
- [ ] `main` からリベース済み、コンフリクト解消済み

## 6. レビュー実施時の具体的手順

### 6.1 レビュアー側
1. **PR 概要確認**: タイトル・説明・関連 Issue 確認、変更範囲把握
2. **CI 確認**: すべてグリーンか、失敗なら作成者に通知して終了
3. **差分確認**: `Files changed` タブで全ファイル目を通す
4. **重点レビュー**: 
   - API 変更 → `docs/api.md` との整合性、型推論影響
   - UI 変更 → ブラウザで動作確認 (可能なら)
   - ロジック変更 → テストケース網羅性、エッジケース
5. **コメント投稿**: 分類ラベル付け、具体的指摘、承認または再レビュー依頼
6. **承認**: すべての `🔴 Must Fix` 解決確認後、Approve

### 6.2 作成者側 (指摘受領時)
1. **即時反応**: 24 時間以内に「確認しました」「対応します」等反応
2. **理解・合意**: 指摘内容理解、納得できない場合は理由付きで議論
3. **修正コミット**: 対応コミット作成、再レビュー依頼 (コメント返信で)
4. **完了報告**: すべて解決後、「すべて対応しました」で再レビュー依頼

## 7. 既知の課題・改善項目

| 課題 | 現状 | 目標 | 対応計画 |
|------|------|------|----------|
| **レビュー負荷集中** | 特定メンバーに偏り | 全員均等 | レビュアー自動アサイン (CODEOWNERS) 導入 |
| **セルフレビュー不足** | PR 作成時チェック漏れ多発 | チェックリスト必須化 | PR テンプレートにチェックリスト埋め込み |
| **設計ドキュメント更新漏れ** | 後回し・漏れ発生 | 同一コミット必須 | CI でドキュメント更新検知 (将来) |
| **Flaky テスト** | 稀に CI 失敗 | 0 件 | 原因特定・修正、隔離 |
| **レビュー遅延** | 24h 目安超過頻発 | 90% 以内達成 | Slack 通知・リマインダー自動化 |
